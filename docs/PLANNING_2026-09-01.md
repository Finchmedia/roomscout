## 3. Product decision: Approve // YOLO (two outreach modes)

The mandate/orchestrator subsystem is **not** a violation of the approval rule — it is the future **YOLO mode**. Restate the hard rule accordingly:

- **Approve mode (default):** the user reviews every outbound message before it is sent (current ApprovalComposer flow).
- **YOLO mode (opt-in):** the agent conducts outreach autonomously without asking per message. The approval gate moves from *every message* to **every binding commitment** — the final "ok, we'll take this room" (contract / booking / firm commitment) still requires explicit human approval of the exact terms.

Implications for the code + docs:
- The hard rule in AGENTS.md becomes: *"Approve mode requires per-message approval; YOLO mode requires per-commitment approval. A binding commitment (contract/booking acceptance) always requires explicit approval of exact terms, in every mode and channel."*
- The mandate's `authorized_by_mandate` decision is legitimate under YOLO — but the mandate scope must define what counts as a "binding commitment" that re-escalates to human approval.
- Reviewers will stop flagging the mandate path as a regression once this is documented; keep the exact-content snapshot + hash mechanics (they're good).
- Fix the operational gaps the review found regardless of mode: no reaper for executions stuck in `claimed/running`, resume/retry double-counts against the daily cap, `expiresAt` not enforced at claim time, killSwitch writes no audit event.

## 5. roomscout.dev — prop portal for controlled demo & flow testing

**Why:** test the full outreach loop (including agent self-registration, verification-code handling, login + native messaging) against a portal we control, so we never spam real listings or message real owners. Honest demo narrative: *"we don't spam real portals, so we built our own."*

**IMPORTANT — role of each auth piece (corrected 2026-09-01):**
- The **portal's own auth = Clerk** (email + password + email verification / one-time codes, out of the box). Simpler than wiring Convex Auth v2 + a mail service, and it gives us real email-verification friction for free. AgentMail is **NOT** part of the portal's auth path.
- **AgentMail = the agent's/band's own mailbox** (e.g. `thecooks@agentmail.to`) that the RoomScout agent uses to **register on the portal**. When Clerk emails a verification code to that address, it lands in the AgentMail inbox and the agent reads it out. This is the real-world use case: to operate on any external platform the agent needs a programmatic inbox to sign up and receive verification mail. (Stronger AgentMail story than sending OTPs ourselves.)

**Two stages, both in scope for this build (this is the V2 messaging portal we discussed):**

Public side:
- Listings: **Gesuche + Angebote** (demand + supply), server-rendered so Firecrawl can crawl/monitor them.
- Own Convex backend, deployed on **Vercel**.

Authed side (this is what makes it a real Browserbase test target):
- **Auth = Clerk** (email/password + email verification codes).
- **Native messaging system** — thread view, send message — the thing the Browserbase agent operates. Deliberately rebuild real-platform friction (session cookies, CSRF, server-rendered forms, scrape-required threads) so it's a real harness, not a mock.

**Agent onboarding flow (AgentMail + Browserbase + OpenAI together — orchestrated, not automatic):**
1. Browserbase session starts registration on roomscout.dev using the AgentMail address.
2. Clerk emails the verification code → it arrives in the **AgentMail inbox**.
3. The orchestrator **polls AgentMail** (API/webhook), extracts the code (OpenAI parsing if needed).
4. The orchestrator **types the code into the Browserbase session**. (The Browserbase session drives only the browser; it has no direct mailbox access — the code must be fetched from AgentMail and injected. This is a strength: a genuine multi-tool loop.)
5. Session persists so subsequent logins/messages reuse it.

**The controlled end-to-end demo story:**
1. Post a new listing on roomscout.dev (live, on camera).
2. Firecrawl monitor detects the change.
3. Signal appears on the RoomScout convex.site index — no refresh.
4. Agent responds to it: (registers if needed via the onboarding flow above,) logs into roomscout.dev with a **persisted session**, writes a message to the owner **via the Browserbase agent**.
5. (Approve mode: user approves the message first. YOLO mode: agent sends, escalates only at commitment.)

**Guardrails:** roomscout.dev is labeled "Demo source" in the registry; the live index still needs 2–3 real public sources for substance (source aggregation + intelligence stay real and shown); only the *sending* flow is confined to our own platform.

**Note on Browserbase (correction to the review's framing):** Browserbase is the missing piece for platforms that expose no email contact (kleinanzeigen.de etc.) — it is strategic, not a gimmick. Not being a hackathon sponsor does not make it a negative; the orchestration still runs on OpenAI intelligence. The only real caution is **video time-budget**: keep the core demo (index → Scout → match → approval → real AgentMail round-trip) tight, and let the Browserbase/portal loop be the strong finale rather than the whole story.

**Repo:** separate project (`roomscout-dev` / roomscout.dev), not inside this repo.

## 6. shadcn UI assessment

**Current state:** Tailwind v4, React 19, `lucide-react`, Radix used directly in 2 hand-rolled components (`ui/SelectField.tsx`, `ui/ActionDialog.tsx`). **shadcn is not initialized** (no `components.json`). Styling is ~805 `className` uses, heavily custom: `btn*` (120×), `rs-*` prefixes, `lcard`, `chip`, plus a 728-line `app.css` and 7 CSS modules. ~10 files hand-roll `<table>` markup (Ops signals/sources/outreach, MusicianInbox, SignalDetail, Profile, panels).

**Verdict: yes to adopting shadcn — incrementally, not a from-scratch rewrite.** You already reach for Radix by hand; shadcn is exactly those primitives with sensible defaults, and it composes into your existing Tailwind v4 setup. A full re-skin is not worth it 3 weeks out and would risk the now-working wiring. Do it as a **targeted, additive migration** where it removes the most hand-rolled surface.

Scope, ordered by payoff:

1. **Init shadcn** (`npx shadcn@latest init`, Tailwind v4 / React 19 path) — creates `components.json` + `lib/utils.ts` (`cn`). Low risk; nothing else changes yet.
2. **Highest payoff — the ~10 `<table>` surfaces →** shadcn **`table`** (+ optionally the TanStack-based data-table pattern for the Ops tables that need sorting/filtering). This is the biggest reduction in hand-rolled markup and directly upgrades the inbox/signals/sources views you flagged.
3. **App shell / sidebar →** `sidebar` block (e.g. `sidebar-07`) to replace the custom `WorkspaceShell` + nav. Good ROI because it standardizes the whole authed frame; medium effort because routing/active-state must be re-wired.
4. **Swap the two hand-rolled Radix wrappers →** shadcn `select`, `dialog`/`sheet` (ActionApprovalSheet is already sheet-shaped). Drop-in, low risk, deletes custom code.
5. **Primitives you use everywhere →** `button` (replaces the 120× `btn` class), `badge` (replaces `chip`), `card` (replaces `lcard`), `input`, `tabs`, `tooltip`. Migrate opportunistically, page by page.

**Do NOT** try to reproduce the 2023 shadcn Mail example (screenshot) — it's a v3-era template, not a current block, and RoomScout's inbox is domain-specific (approval state, provenance, channels) rather than a generic mail client. Build the inbox from `table` + `card` + `sheet` primitives instead of porting that template.

**Recommended cut for the hackathon:** steps 1–2 now (init + tables) give ~80% of the "feels solid, not scaffolded" benefit for a fraction of the effort. Steps 3–5 are a post-submission polish track. Keep MarketGlobe (Mapbox) and RealtimeVoiceScout as-is — they're custom for good reasons.
